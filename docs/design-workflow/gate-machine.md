# The gate's machine

What `node scripts/gate.mjs` does, for whoever runs or maintains it. The judge's brief is [briefs/gate.md](briefs/gate.md); the design behind this is [gate-v2.md](gate-v2.md) and [gate-simplify.md](gate-simplify.md).

**The machine is the merge gate** (owner, 2026-10-20): the owner's "PR it" is the design approval, so a mechanical pass posts `sentri/gate` success whether or not screens moved, and a mechanical fail posts failure. The judge ([briefs/gate.md](briefs/gate.md)) is advice the builder may ask for; it never holds a merge.

**English first** (owner, 2026-10-21): Chinese is checked only on a frozen feature (every current screen approved; the atlas's `frozen` status). Until a feature freezes, its ZH runs and ZH leaves don't run in the gate and don't hold a merge; the Chinese pass belongs to the freeze ([freeze-checklist.md](freeze-checklist.md)).

`node scripts/gate.mjs` is the mechanical part of the gate. The driver runs it from any checkout of this repo. Its work is one call, `evaluate(base, candidate, mode)` in `scripts/evaluate.mjs`, which answers **pass**, **fail** or **blocked** ([gate-v2.md](gate-v2.md)):
- It judges with main's rules. When the checkout it runs from has `scripts/`, `docs/design-workflow/` or `package.json` different from main (a branch, a stale main, uncommitted edits), it runs main's own `gate.mjs` from a worktree of main, with the same arguments, and removes that worktree after.
- It refuses a candidate that doesn't contain `origin/main`.
- It makes both worktrees and runs §1 on the candidate. **The rules the diff decides come first**: the candidate contains main, `atlas.json` is regenerated, no conflict markers, no lost behaviour coverage, no visual declaration (colour, type, spacing, border …) added to a page file under `ux/` outside `ux/design-system` (P2, [build.md §3](briefs/build.md)), and the library organised (every component folder in `_groups.json` or retired in its `gate.json`; a new `SentriUI` export stamps a grouped component or is named in its README), whether or not a screen moves. When one fails, the gate stops before any browser work (`mechanical.json`'s `stoppedEarly`), so the failure arrives in seconds rather than after the full run. Fix it and gate again: the screens are checked then.
- **The reach is what the evidence identities say** (gate-simplify.md X1): every screen and component page whose shot identity differs between base and candidate, and every screen only one side has. The scope brings in nothing of its own: it is a declaration for the known-reach check (gate-simplify.md X7). A screen with the same identity on both sides shares one shot, so its diff is 0 by definition and it is not shot at all; nothing else is shot as a tripwire. Leaves the same way: every leaf whose identity differs at some run, or that base doesn't have. A screen in the reach is shot on both sides at three runs: EN at 390 and 360, and ZH at 360, its worst case for fit (gate-simplify.md S4). It changed if any of those differs. `mechanical.json`'s `reach` counts what changed and what was added or removed.
- **The guarantee is that the identity is complete.** A screen's identity hashes its page closure from the static analyser (`identityInputs`, gate-v2 §2): every file the page, its scripts, frames, stylesheets and `<style>` blocks load, the bundle units it can run, with every start-up effect of the bundle (each constant's initialiser and setup statement, with what it reads), and what renders of its atlas entry. A load the analyser can't bound hashes every page-loadable file of that kind. Stylesheets are read only in one syntax: `@charset`, then lowercase `@import "…"` or `@import url(…)` before any rule, and `url(…)` for fonts and images. Any other import (another case, an escape, after a rule) makes the pages that load it hash every stylesheet, and `image-set()` naming a file by a string makes them hash every media file. **`node scripts/gate.mjs --audit`**, run by hand weekly on main, draws every screen afresh at every run and compares it with the stored shot of the same identity: a difference is an identity that misses an input or a screen that doesn't draw the same twice, and is fixed in the analyser or the screen.
- It escalates the class to **shared** when the bundle, the tokens, a file that pages of two or more features load (e.g. `ux/system/astra-surfaces.js`), or another feature's screens change.
- **A shared change's reach is scoped** (owner, 2026-10-20). Of the screens the identities reach, it keeps the PR's own features (their `features/<id>/` files, the scope, or a page file only their pages load (a file two or more features load is shared); the design system, the strings and the atlas own no feature), the component pages of the parts it touches, calls or styles, and the features in progress, read from main's `features/_in-progress.json`. The in-progress features' screens are **propagation** screens: their pairs carry `propagation`, the judge says only propagated or broken, and `mechanical.json`'s `propagation` lists which changed exports each one calls (`notUsingShared` on a moved screen that calls none: likely a local copy). The mechanical checks still run on them. **Every other screen the identities reach gets the quick check** (owner, 2026-10-22, after #264 broke Health record's Conditions sheet out of scope and nothing saw it): one run, EN at 390, on both sides, with that run's visit checks (spacing, legibility, headers) and "no screen broken". A new defect against base fails the gate exactly as on a changed screen (one main already has there is main's debt). No 360, no ZH, no leaves; its pairs are made as usual and marked `outside: true`. `outOfScope` counts these screens, `outside` says how many were checked, which moved and how many new defects they have, and `results.md` says it in one line ("Outside the scope: N screens checked (390 EN), M moved: …; K new defects"). A component page the scope drops is not checked. **Reach by rule** (2026-10-22): a `bundle.css` edit keeps the component pages a changed rule may style (`scripts/css-reach.mjs`). The stylesheet is split into rules with their `@media`/`@layer`/`@supports` context; the changed ones are those outside a longest common subsequence of base's and the candidate's rules (a moved rule is changed). A rule may style a page when every class one of its selectors requires (attribute selectors and the arguments of `:not`/`:is`/`:where`/`:has` dropped) can occur in the page's markup: the class-shaped words of the variant file, what it loads and the bundle units its scripts can run with every start-up effect (`variantInputs`), on either side. A word at a string boundary of three characters or more stands for every class it starts (`'st-toast--'+tone`) or ends; a word written as `.name` reads a class and makes none. Whatever it can't name reaches every page: a selector with no class (`:root`, `body`, `*`, attribute-only), any other at-rule (`@import`, `@font-face`; a `@keyframes` reaches what the rules that name it reach, and markup that names it), a rule with rules nested in it, an `@import` that is not (or stops being) at the head of the stylesheet, a stylesheet it can't split, a page whose loads can't be bounded. This is scope, not identity: every shot and state identity still hashes `bundle.css` whole, and the screens' reach is unchanged. `node scripts/css-reach-proof.mjs` checks it against what renders: on every component state, every class in the DOM and every selector that matches it must be attributed to that page; run it after a change to how `bundle.js` or a variant builds class names. `mechanical.json`'s `cssReach` says how many rules changed and whether they were narrowed. Only the own and in-progress features' leaves run. A refactor and a change that isn't shared keep the whole reach. The identities are not changed by this.
- **Evidence is kept by identity** (gate-v2 §3): every shot, visit check, state check, leaf run and repository check has an identity hashing everything it depends on (the table is in gate-v2.md §3), and a result is reused only on a matching identity, from the store in the git common dir (`sentri-gate/evidence/`). Base evidence stays while its main is one of main's last ten commits; candidate evidence is computed only for identities the store doesn't hold. A rerun of the same candidate reuses everything; a checker that changes on main recomputes exactly the results it produces. `mechanical.json`'s `evidence` says how much was reused and computed.
- **One scheduler for all browser work**, four at once (`scripts/machine.mjs`; it goes lower under load), in one browser. **One prepared visit per screen state**: the shot and the legibility, spacing and header checks read the same page. A visit settles first (fonts loaded, no scroll moving, no timer due soon, no request in flight, then a quiet window) and is shot twice a quiet window apart; a screen that doesn't settle, that moves after it settled, or that a second visit draws differently is **unstable**, and the gate **blocks**: it never picks the good-looking shot. A changed screen is visited once more on each side, fresh, and must draw exactly its own shot again.
- **Machine errors** (a navigation timeout, `net::ERR_*`) are retried once, alone, after the queue drains. A second one blocks the gate. Every other failure stands, and nothing passes because it passed when run alone.
- **The inventory is reconciled on both sides**: an added screen is listed under `inventory.added` and needs its own pass or fail; a removed one under `inventory.removed` and needs a reason under `gone`; a run that should have evidence and has none blocks the gate. Missing evidence is never unchanged.
- **One gate runs at a time on a machine, in turn** (`scripts/gate-queue.mjs`). A gate takes a ticket in `sentri-gate/queue/` and gets the lock when no live ticket is ahead of it: first come, first served, except that a `--verdict` re-gate after main moved goes ahead of ordinary gates (it takes seconds when nothing intersects and is all that stands between a judged PR and its merge); it never stops the gate running. A ticket or lock whose process is gone is dropped. While it waits a gate prints who holds the lock, what it gates, for how long, and its place in the queue. No other browser run from this repo shares the machine with a gate either: `npm test`'s browser suites, `run-scenarios`, `check-states` or `shoot-screens` started on their own wait while a gate runs or is queued, and a gate waits for those already running to end (they may run beside each other), but not for one that hasn't worked (beaten, i.e. used the CPU) for 10 minutes: that is a leftover, and the gate names it and goes. Inside the gate, `npm test` holds two of the scheduler's four slots. A gate stopped by a signal (Ctrl+C) first closes what its run opened, awaited: the servers and `npm test`'s whole process tree (`taskkill /T` on Windows), the browsers, then the worktrees; only then does its lock go. A second signal exits at once.
- It fails a candidate that removes behaviour coverage (`scripts/run-scenarios.mjs`, a feature's `scenarios.json`, or a leaf), leaf by leaf: a leaf that runs on base and is gone, made `pending`, or makes fewer assertions on the candidate is lost coverage, whatever the count of leaves. A kept leaf is compared assertion by assertion (its contract: everything but `says`): the same target with a weaker qualifier (a dropped `hard` tag, a dropped `zh`, `enabled`/`disabled` made present, a wider scope for something shown or a narrower one for something absent), a new assertion any page satisfies (a constant `expr`, `body`, empty text), `clip: false`, or fewer widths or languages is lost coverage too. An assertion rewritten to a new target (the design changed what the leaf checks) is kept and listed under the gaps. That is its own workflow PR. A leaf that moves to another feature keeping its id (features merged or split) is kept coverage where it lands, under the same tests; a `scenarios.json` whose every leaf moved is not lost.
- It writes `mechanical.json` (`outcome`: pass, fail or blocked, and `blocked` with the reasons), plus `pairs/<screen>/<lang>-<width>.png` (base | candidate) for every changed, new or removed screen; a missing side reads "not on this side". Each pair in `mechanical.json` has a `kind` (changed, new, gone), a `pct` (0 means pixel-identical), the `identity` of each side's shot and the `image`, each side's shot by its bytes.
- A screen's identity hashes only what renders of its atlas entry (url, preset and steps) and, of `atlas/atlas.json`, only that for the screens on its pages: the bare harness hands a page nothing else. A notes edit, an approval or a rebuilt atlas re-shoots nothing.
- **Component pages are screens too** (ledger L23). Every variant page the atlas draws (Components → <Name> → <variant>) is shot like a screen, in EN only (its Chinese cells are its own states): at 390 and 360 when it is in the reach, and not at all otherwise. The shot is the atlas's own state grid, each state's frame at that width, two to a row, whole. Its id is `ds:<Name>/<variant>`, its feature `design-system`, and its pairs are `pairs/ds_<Name>/<variant>/en-<width>.png`. Judge them exactly like a screen's (§3–4): the page teaches the law, so a state that breaks it is a defect, and a page that moved needs a better pair to pass. A change that moves a component page is at least **presentation**, never copy only. A component page is in scope when SCOPE names `design-system` or the change edits that component's own folder (`ux/design-system/components/<Name>/`); another component's page moving is outside it (known reach).

An optional judge reviews from those pairs and writes `verdict.json` beside them; `node scripts/gate.mjs --verdict <out>` checks it (another commit, an unjudged or unlisted pair, a worse or failed pair, a blocked gate) and prints the result. It posts no status: the judge is advice.

**A pass GitHub did not take** (2026-10-21): when the status post fails (this machine's GitHub calls often hit TLS/EOF), the gate prints NOT POSTED and exits 4, never the merge command. `node scripts/gate.mjs --post <out>` posts that run's pass without gating again, only while the PR head and main are the ones it gated and no later run on the same commit (finished, crashed or killed) has replaced it.

**Re-checks go first** (2026-10-21): a branch that has passed on this machine before takes its next gate ahead of first gates, since that re-check is all that stands between an approved PR and its merge.

**A ux/system stylesheet edit names its feature** (2026-10-21): `ux/system/*.css` is one page's stylesheet or the whole system's, and the diff cannot tell which. A change that edits one without a `features/<id>/` file or `--scope` stops early and asks: `--scope <feature>` for a page's own stylesheet, `--scope design-system` for a shared one.

**Trying the gate's own tools** (2026-10-21): `node scripts/gate.mjs --try --candidate <ref>` runs this checkout's tools, not main's, against origin/main, and posts no status. A change to the gate is tried this way on a real PR before it merges; a try run never merges anything.

**A moved main never voids work by itself.** When main moves on (before the judge has run, or after), merge it forward and run `--verdict <out>` on the judged run as usual. Seeing the head or main moved, it gates the new head against the new main into `<out>/regate-<head>-<main>/`, reusing every result whose identity is unchanged (a shot that was already confirmed is not visited again), and carries every judgement to the pair of the new manifest that shows the same two images (same screen, run and kind, and each side's shot the same bytes, or the same shot identities for a run that recorded no images), with each removed screen's reason. A walk is about behaviour, so it carries only for a screen whose inputs are unchanged too: a screen that shows the same picture from changed inputs (a page script, a handler) keeps its pair verdicts and is listed to be walked again. A screen named to be walked because it runs changed code and draws the same (G15) has no pair: its walk carries when it runs the same inputs as when it was walked (`walkIdentity` in mechanical.json; a run without it walks every such screen again). A verdict with no pair at all carries whole (its walks, calibration and claims), so a behaviour-only change re-walks only the screens main's new commits reach, and needs no new walk or judge when they reach none. Only the judged run's own verdicts carry: a verdict stamped for another candidate or base, or two that judge one pair differently, carries nothing and fails as checkVerdict fails it. When every pair carries, it decides on the carried verdict at once: a main that moved by a file no shot depends on costs no reshoot and no new judgement. Otherwise it lists the pairs whose images changed: a judge decides only those, in `verdict-new.json` beside `verdict-carried.json`, and `--verdict` runs on that folder. Anything that matters (a new failure, a block, a changed image) still has to pass. There is no `--carry`.

The gate posts its result as the `sentri/gate` commit status on GitHub (`--verdict` posts none). Every GitHub call the gate makes (the queue, PR files, statuses) is tried twice more after a network error (EOF, TLS, a timeout, a 5xx); after that it says `GitHub could not be reached`, which is not a queue verdict or a status: run it again. An answer from GitHub is never retried. Branch protection on main requires it, with the branch up to date with main (gate-simplify.md G2), so GitHub refuses an ungated merge, or one gated against an older main, however it is attempted. A gate run posts `pending` when it starts and `failure` when it fails or blocks, so the status is the one record; there are no local pass records. The local merge guard (`scripts/merge-guard.mjs`) only holds our own sessions to the one merge form, pinned to the gated commit; it is not the boundary.

**Every change merges on the mechanical gate** (owner, 2026-10-20), moved screens and changed runtime code included. `walkNeed` still lists the screens that run changed code and draw the same, for a builder who wants a walk; it holds nothing.

A review too big for one judge may be split by feature: each judge writes `verdict-<feature>.json`, and `--verdict` reads them together. It is advice either way.

## The mechanical checks (P2, P5; any failure fails the gate)

The gate runs each of these on CANDIDATE, through its one scheduler, and records it in `mechanical.json`'s `checks`. The commands named are how each check runs on its own.
1. `npm test`. All pass. Skips must state a reason.
2. `npm run check`. It also runs the farm legibility check in report mode. It must report the atlas OK. `npm run atlas` must produce no diff in `atlas/atlas.json` (it carries no build stamps; the published site stamps its own copy).
3. **Farm legibility, blocking for changed screens.** Run `node scripts/check-legibility.mjs --changed <the SCREENS ids> --strict` on CANDIDATE. It renders each screen bare at 390×844. While `docs/design-workflow/README.md` says `Legibility gate: strict`, a screen in scope fails on any violation: text under 11px, or under 13px inside a control, contrast under 4.5:1 (7:1 for 16px+ primary values), or a target under 48×48 (an invisible hit area counts). If that line ever says `no-regression`, or the change is declared **shared component**, pass `--compare <BASE url>` instead of `--strict`; a screen in scope then fails only if it has more violations than at BASE in any category, or a violation on an element that had none. Screens outside `--changed` are reported, not blocking. Any failure ends the gate. The 16px body floor and "ink, not pale grey" are judged by eye in step 3. Crowding is fixed by tightening copy and layout, never by shrinking type. Law: `ux/design-system/README.md`.
4. `git grep -n '^<<<<<<<\|^>>>>>>>'` finds nothing.
4b. **Clear spacing (P4)** on changed screens: `scripts/check-spacing.mjs` (a block closer to a list than its rows, crowded boxes, doubled lines, a scroll container that shows a desktop scrollbar: L27, or that scrolls sideways though its content is not a row: L28, a section heading closer to the block above than to the content it labels, or a row's trailing control off its row's centre: L33). It runs on the out-of-scope screens' quick check too. A defect main already has there is main's; only a new one fails.
4c. **Headers (P3)** on changed screens: `scripts/check-headers.mjs` (the Headers law: 24px from the header to the body; nothing acting in a header but Back, the subject chip and a sheet's corner actions (Clear or Reset top right, ✕ top left), each a 48px target centred ±2px on the title and its line; no count in the title or line; the line on one line, and the title on one line 12px clear of the corner targets, at 360 in EN and ZH). Its known-bad fixtures are `scripts/check-headers.fixtures/` (`--self-test`). A defect main already has there is main's; only a new one fails. The moved component pages get the same check (`check-headers.mjs --components <Name,…>`: room, wrap, contents and corner at 360 on every state the atlas draws), base against candidate by page and detail: "component pages follow the Headers law (P3)".
4d. **Motion has a held frame (P4, L25)**: every `@keyframes` the change adds or alters under `ux/` is named in some screen's `holds` (atlas/SCHEMA.md), so its cue is shot and paired like any screen. A held screen is judged like a screen; render it also as a person opening the atlas does (fonts from the network, `atlas/index.html?feature=<id>&screen=<id>`), since the gate's shooter serves fonts locally and a late font is a different layout.
5. For every class: `node scripts/check-states.mjs`. It renders every design-system state the way the atlas draws it and writes `review/state-check.json`; its known-bad fixtures (`scripts/check-states.fixtures/`) are the rejected examples it already catches. If the component has its own check script (e.g. `node scripts/check-button-components.cjs`), run that too, with the server running. Set `SENTRI_PREVIEW_ORIGIN` and `SENTRI_PLAYWRIGHT`. No console errors, no target under 48px, no horizontal overflow. The gate renders the states of every variant file whose identity differs between base and candidate (or that one side has), each result kept by identity: the file, what it loads and the bundle units its scripts can call with every start-up effect (`variantInputs`), plus the tokens, the bundle's CSS and the fonts, so a bundle edit re-checks only the variants that can run what changed (a variant that aliases the namespace with `var` hashes every unit). A shared change checks only the component pages its scope keeps (for a `bundle.css` edit, the variants a changed rule may style: Reach by rule above). `mechanical.json`'s `reach.states` counts them; a state whose resource failed to load (`net::ERR_*`) is the machine: retried once, and blocked the second time, never counted or dropped.
6. For behaviour (and presentation that touches a walked screen): `node scripts/run-scenarios.mjs` for each affected feature. Every leaf the change touches passes, at 360 (the narrowest width its spec lists, unless the leaf names its own) in EN and in ZH. A ZH run goes only where the leaf's start renders Chinese: one ZH run per start goes first, and when it finds none, the others from that start are blocked the same way without running (gate-simplify.md S5, X8). A blocked leaf stays blocked; it never becomes a pass. Every run the gate asks for is required (ZH only on a frozen feature), so a candidate run that comes back blocked because its page renders no Chinese blocks the gate and is never stored; a decision-blocker is a row of the report, not a run, and stays blocked without holding the gate. A fresh failure is run once more on the same identity before it is stored: the same failure again (the same assertion contracts broken the same way) is a design result; a pass, or a different failure, blocks the gate as an unstable leaf (L26), to be fixed in the leaf or the page, never retried away; a confirming run that could not run blocks too. The gate runs the leaves through its one scheduler with everything else. A run whose only failures are machine errors (a navigation timeout, `net::ERR_*`) is retried once, alone; a second machine error blocks the gate, which is the machine, not the design: rerun the gate when it is idle. An assertion failure never retries. A leaf that fails on the candidate is asked again on base, and the two reports are compared run by run: a failure is main's debt (a gap that names it) only when base fails the same leaf at the same width and language with the same assertion contract (the definition that failed, fingerprinted by the runner) and the same failure category (missing control, timeout, wrong text, page error, preset missing …); a failure whose contract or category is unknown is never debt. Any other failure in that leaf, including one at another width or language, is this change's, and with no base report none is debt (owner, 2026-10-15; review of the gate, 2026-10-16). A run that crashes or reads a bad tree fails as it is.
7. For copy: every changed string meets the copy budget, uses a verb from `ux/laws/strings.json` with its one meaning, and renders in EN and ZH without clipping.

## The Results block (gate-simplify.md S8)

Every run writes `results.md` beside `mechanical.json`: the outcome, the class, the reach, what moved, every check with its result, the leaves, `npm test` and the gaps, all measured on the gated commit. It is the PR's Results block, pasted whole. A PR body states no measurements of its own (test counts, pixel differences, sizes, "identical"): the gate's are on the right commit by construction, and a builder's go stale with the next push (#163, #192).
