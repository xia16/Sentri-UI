# Sow action drawer — primary-source navigation guidance

Researched 2026-09-17. Scope: a mobile sow action drawer with Inspection-style rows, a fixed header/footer, optional Health / Records / Feed / Production switching, and one link to unavailable actions and reasons. Research only; no UI changed.

## Findings and application

1. **Choose category behavior before borrowing a control's appearance.** Apple recommends segmented controls for closely related subviews on iPhone/iPad, including an example inside Calendar's New Event sheet. It recommends around five segments or fewer on iPhone, noun labels, and consistent behavior across segments. **Application:** mutually exclusive Health / Records / Feed / Production lists would fit that interpretation. A sticky row that jumps to headings in one continuous list is a different interaction: use category links and a current-section indicator rather than imply that all other categories have been filtered away. The latter is the current product recommendation, not something this segmented-control guidance directly establishes. [Apple: Segmented controls](https://developer.apple.com/design/human-interface-guidelines/segmented-controls) ([official page data](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/segmented-controls.json)).

2. **Keep category navigation distinct from the app's main navigation.** Apple describes tab bars as navigation between top-level app sections, not action controls. **Recommendation:** put the category row near the action list under the sow identity/title, rather than adding a second bottom app-navigation bar. The categories organize actions for this sow; they should retain the current sow and drawer context. Whether Records belongs here depends on whether its rows are sow-related actions or navigation into a separate records area. [Apple: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars).

3. **Reduce scanning with meaningful grouping, not deeper nesting.** Apple recommends important/frequent commands first, grouping related commands, reconsidering long menus, and generally limiting submenus to one level. **Recommendation:** retain familiar labeled action rows under visible category headings, in a stable order. A sticky category row can provide shortcuts through that continuous list without introducing category → subgroup → action nesting. Add it only if the real available-action inventory is long enough to justify it: a few visible grouped rows may already be faster. The sources do not establish a numerical threshold or recommend sticky jump links specifically. [Apple: Menus](https://developer.apple.com/design/human-interface-guidelines/menus) ([official page data](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/menus.json)).

4. **One unavailable-actions link is a product choice with a useful platform analogy, not a universal rule.** Apple's context-menu guidance says to hide unavailable items because this menu is specific to the current content; its ordinary-menu guidance instead keeps unavailable commands discoverable, usually dimmed. **Recommendation:** follow the requested single link, such as “Unavailable actions · 3”, opening names and concrete reasons. This preserves discovery without mixing inactive rows into the working list. Keep the link at drawer level so changing categories does not conceal it. Do not claim Apple requires this hybrid: the custom drawer is not automatically a native context menu. [Apple: Context menus](https://developer.apple.com/design/human-interface-guidelines/context-menus), [Apple: Menus](https://developer.apple.com/design/human-interface-guidelines/menus).

5. **Keep reasons in a shallow flow and give the list enough room.** Apple defines sheets as scoped tasks, advises against displaying one sheet over another, distinguishes Back from dismissal, and permits a large sheet when content benefits from the space. **Recommendation:** the unavailable link opens a secondary view within the same drawer, with Back restoring the list position. Retain an obvious way to close the drawer. Fixed header/footer is an existing design constraint, not a requirement established by this guidance; verify that the scroll region still exposes every row on small screens. [Apple: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets) ([official page data](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/sheets.json)).

## Limits and review criteria

- These are platform recommendations and our product interpretation, not evidence that category switching beats scrolling for farm workers. Compare prototypes with the actual action counts, frequent tasks, smallest supported phone, and enlarged text.
- Health / Records / Feed / Production must be understandable and sufficiently distinct. Check ambiguous actions with representative users before treating this taxonomy as settled.
- For this requested continuous list, omit categories containing only unavailable actions and expose those actions through the single reasons link. Keep the remaining categories in fixed relative order; do not personalize or reorder them as the user browses. If saving an action changes eligibility, update the list with clear save feedback. This follows the user’s space constraint and is our recommendation, not a quoted platform mandate.
- Apple does not prescribe the requested one-link reasons pattern, the existing row appearance, or fixed header/footer. Its generic sheet saving examples do not determine this product's save semantics.
- Material 3 tabs and bottom-sheet pages returned JavaScript-only content during this bounded check. No detailed Material recommendation is claimed. Apple official page data was used where the rendered HIG page also required JavaScript.
