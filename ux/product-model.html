One product model

Reconciling the two production surfaces — 生产任务 (scheduled tasks) and 巡检 (inspection) — into a single coherent product, on the design system we have already built.

synthesis of: components.html + screens.html · 7 task docs · pig-actions.html · inspection PRD + 6 parts · ~290 production screens

1 · The problem we actually have

Two production files describe two apps that overlap heavily and agree on almost nothing:

Seven actions are specified twice — fostering, death reporting, treatment, transfer, health management, weaning and farrowing — with different flows, different bulk rules, different gating. Neither file references the other. Production's own consequence of this shows up as an instruction to the farmer: after fostering, 请在寄养后同步转出与接收栏位的任务进度 — "please manually sync the task progress of both pens." The system asks a human to reconcile its two halves.

2 · The claim that unifies them

Tasks do not own records. They observe events. An event is something that happened to an animal — she came into heat, she aborted, she weighs 182 kg, she died. A task is a question the system asks about a cohort — "which of these 200 sows are in heat?" — with a window, a target and a progress reading. The same event can be discovered while doing scheduled work or while walking a unit. So the event is the record; the task is a view over the events it expects. Record a farrowing during a check-in and the farrowing task advances by construction — because the task was only ever counting farrowing events for its cohort.

This single move dissolves the largest problems in both files:

Production problemWhy it disappears
"Manually sync both pens' task progress" after fosteringNothing to sync. The foster event changed both litters; every task counting those litters re-derives.
分娩 and 断奶 exist as both a task and an inspection tile, with different formsOne event, one form. Two doors into it.
Submit ceremonies that "certify" a roundEvents are the record; a task's progress is derived, never asserted.
Ended-task clone modules (a second read-only app per task)Events persist independently of the task that observed them; history is the event log.
Two ad-hoc menus with different contentsOne event catalogue, surfaced identically everywhere.

5 · Four laws

Law 1 · The subject decides the surface. One pig → her sheet's ⋯. Several pigs → the list's selection bar. No pig yet → Today, or a unit. A farmer never has to remember which menu holds an action; only how many animals he is talking about. This replaces production's six entry surfaces and two menu vocabularies.
Law 2 · The payload decides bulk. Production wrote this rule twice and never generalised it. Generalised: • Per-animal payload → single only. Every reproductive event (its own timestamp and batch consequence) and every measurement (its own value). • Shared payload → bulk. Treatment, triage, condition, transfer, 留种, missing — one form, N animals. • Shared selection, per-animal payload → bulk selection, individual detail. Death is the only one: pick the animals together, give each its own cause. Derivable, so no per-action configuration table has to be maintained — and it agrees with both of production's written lists.
Law 3 · The animal's state decides availability — never the surface. Production gates by task stage (生产任务) or by selection eligibility (巡检). Both are proxies. Gate on the animal: is she bred? does she have a live litter? is she identified? is she located? Then the same catalogue appears everywhere, unavailable rows disabled with a reason, and nothing can leak into a context where it cannot apply — which is why 流产 currently appears in piglet processing. Partial eligibility must be visible. Production runs the op on the eligible subset and silently drops the rest. Instead: list the blocked animals with the reason, and let the farmer proceed with the remainder deliberately.
Law 4 · One record, two doors. An event captured during a check-in and the same event captured during a task are the same record, the same form, the same validation. The only difference is the pre-fill and where you return to. No duplicate flows, no reconciliation step, no "sync progress manually".

6 · Identity — the concern we had not handled

Our design so far assumed every pig has an ear tag. The inspection file proves otherwise: un-identified pigs exist in numbers, and nearly every behaviour forks on it. This is the largest addition to the system.

WhereBehaviour required
Row selectionAn un-identified row represents N head, not one animal. Ticking it must ask how many — production's inline ✕ [− n +] ✓ stepper — and the row reads 已选 n/N. Whole-pen selection forbids the quantity (it means "all").
SearchAccepts ear tag or ear notch. Three task docs flagged this independently.
ScanNFC ear tag, with the notch picker (two tappable ear diagrams) as the manual fallback.
Preconditions留种 requires identity — 系统强制要求在标记为育种之前进行打耳标 — plus sex. Blocked rows must offer Assign identity inline rather than failing.
TransferAll-identified → one-tap. Contains un-identified → the longer path where pen-level health records are marked move or copy.
FosteringNo identities → count stepper. Any identities → itemised list. Identity supplement only when the receiving pen has already done tag/notch/weight.
Assign identity is one event, reachable from anywhere it is a precondition. Ear tag* and sex* are the only required fields; notch and parents are optional (parents derived when known, searched or scanned when not). It appears inline in 留种, in piglet processing, in fostering, and from the pig's ⋯ — always the same three steps.

8 · Open decisions

Real product questions surfaced by the reconciliation, in the order they block work.

1 · Does a check-in have a completion state at all? Settled. Production's 提交巡检 asserts 所有栏位与设备已检查完毕 but nothing validates it, and it is offered from a single-pen drill-down. It is not a submission: every condition, treatment and mark was written the moment it was recorded, so there is nothing left to send. What remains unclaimed is the negative — that a named person covered the unit and found nothing further — and that is the one fact the system cannot derive. So the act survives, but as a stamp of unit · person · time in the unit header, not a button at the door: checked 09:41 · G. Hansen. Repeatable, never a coverage claim. No submit button exists anywhere in the product. Environment readings are their own small event beside it. See components.html 05.
2 · What makes an animal ineligible for an event? Production shows the partial-eligibility dialog but never defines eligibility. We need the actual per-event preconditions (§4 gives the obvious ones; the rest need the domain).
3 · Weight: group or individual? Two incompatible models in the file, plus a third unplaced variant, plus an annotation saying weight is single-pig-only while six frames show a group model. This is a data-model question, not a UI one.
4 · What distinguishes 移除 from 康复? Remove vs recovered share one screen and one submit in production, with nothing stating the difference. They are probably "this was never true" vs "this is no longer true" — which matters for health history.
5 · The four triage levels have no semantics. Every description in the file is placeholder text. Needs a veterinary definition before it can drive anything.
6 · Is fostering bulk? 巡检 lists it bulk-capable; the flow picks one counterpart sow. Most likely "N" means N piglets moved, not N sows acted on — confirm.
7 · Equipment scope. Fault resolution has a button and no screen anywhere; feed stations are fully designed but marked 本期不开发. Decide whether equipment ships with the first release or is a later subject.
8 · Where do records get browsed? Both files gesture at a toolbox holding lists (death records, missing pigs) without designing them. If events are first-class, an event log per animal and per unit is the natural home — and it replaces the ended-task clone modules.
